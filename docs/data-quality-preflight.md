# Data quality preflight

Step 3 of the wizard now includes **Check All Selected Tables**. It saves the current plan and scans every selected source table, using the saved mappings and the live target schema. The preview is read-only on both databases. The existing first-row dry run remains a separate mapping check.

Every migration, including a retry or execution dry run, repeats the full audit automatically. A stale preview cannot authorize a different selection or changed source data. The runner imports only accepted rows from that run's audited snapshot. The transaction date/link filter applies to the audit as well as the import; master data remains unfiltered.

## Outcomes

The scan now prepares automatic repairs as well as exclusions. Identical full source/mapped copies sharing a primary key keep one copy; conflicting values still require a decision. Internal labour-line (`work_done.wdid`) and supplier-invoice-line (`invoice_items.invid`) IDs can be regenerated for empty or explicitly replaced destinations. This is disabled for retries, existing destination data, declared dependencies, lookup references, and populated application-managed ID links. Invoice numbers, job numbers and stock identities are never manufactured.

Use **Review Records and Make Corrections** for a readable, paginated list of affected source records. Corrected field values are saved separately for this tenant, with the original source record retained, and applied to the migration snapshot during the next scan. They apply only when the original record still matches; changed source records need fresh review. **Undo saved correction** removes an override. These corrections do not modify Firebird and must pass the full audit again. **Download Readable Summary** is an HTML summary with the displayed page of records; JSON files remain under Technical exports.

For records that should not be imported, **Exclude unresolved source records and rescan** offers bulk quarantine. The UI confirms the current affected count and explains that financial transactions and opening balances may be affected. This opt-in plan policy also excludes dependent rows rejected by relationship checks, preserves evidence, and is reapplied by the execution audit. It does not bypass missing mappings or other configuration errors. Add missing parent tables first. The report clearly shows when this policy is enabled, with a control to disable it and rescan. Choosing the bulk action also sets selected tables to INSERT/SKIP with Truncate first disabled, retaining existing destination records. Later explicit changes to those plan settings still apply.

- **Accepted:** satisfies the applicable checks and is eligible for import.
- **Quarantined:** a confirmed exclusion such as an empty required business identity or a legacy REDO invoice. Full original rows and reasons remain available. Missing identities on records carrying quantities or money require review instead.
- **Review:** conflicting keys, missing parents, invalid values, lossy conversions, or ambiguous records. These block the entire run before target cleanup or data import, even with Continue on Error enabled.
- **Configuration error:** missing tables/columns, missing required mappings, unsupported constraints, or an unusable lookup. These also block the run.

The legacy `.fdb` is never cleaned by DELETE statements. This replaces the former unconditional invoice/payment/job-reference deletions. Automatic staff deletion has also been removed; target clearing uses the selected table's explicit **Truncate first** option.

## Checks and scope

For generated-column metadata with escaped quote delimiters, the checker reads the executable expression from `SHOW CREATE TABLE` instead of unescaping string contents. This handles [MySQL's reported metadata escaping behaviour](https://bugs.mysql.com/bug.php?id=104294). SQL syntax or unknown-column errors stop the audit as checker/schema failures rather than classifying every row as dirty. The results panel provides next steps for missing parent tables, existing-target conflicts and duplicate identifiers.

Every selected table gets checks derived from live MySQL column metadata, primary and unique keys, foreign keys, and mapping lookups. These include nullability, blank required text, numeric ranges and decimal precision, string lengths, dates, ENUM and JSON values, mapping transforms/defaults, duplicate source keys across batches, and conflicts with existing target keys. Generated columns and CHECK expressions are evaluated by MySQL using parameterized SELECT statements, without inserting temporary business records. Functional/prefix unique indexes that cannot be validated are reported as blockers.

`src/migrate/dataQuality/rules.js` supplements schema checks with explicit business identities and relationships for invoices, stock, jobs, parts, labour, payments, suppliers and associated records. Nullable columns are not automatically treated as required. In particular, an open-job part or labour line may have a NULL invoice number; a general invoice may have job number zero. Table-specific business rules must be added to this registry when new application requirements are introduced; a schema alone cannot infer every business rule or prove that accounting balances are correct.

Selected parents are checked against accepted rows, after exclusions. Missing or rejected parents block child records rather than silently deleting them. Unselected parents are checked in the existing target, because a parent that exists only in legacy data will not be present after migration. Relationships to rekeyed parents require an explicit lookup and appropriate migration order. When a selected parent will be truncated, existing target child references are checked as well, including children outside the selected tables.

Duplicate source identities require review; the previous invoice rule that selected one duplicate header has been removed from the runner. Existing invoices with the same invoice number, job and customer remain eligible for the runner's existing-record skip behavior. Identity conflicts block the audit.

## Reports and recovery

Completed results are saved with their plan ID and restored when Step 3 opens again. Returning from record details or grouped decisions also carries the audit ID, including reports created before plan-linked history existed. Results remain visible when settings or saved corrections change, with a stale-result notice. Opening a report does not start a new scan. Execution still runs its own full check. Older reports can be discovered automatically only when their source, complete table selection, mappings and configuration match exactly.

**Review grouped repair decisions** organizes findings by the original problem and includes linked affected records. A REDO invoice and its blocked credit notes appear in one group; users are not prompted to invent a new invoice number for the credit note. Each group has a preview before saving. Shared invalid values can be corrected across matching records. Existing-target conflicts can be resolved by explicitly leaving the conflicting source group out while retaining destination records. Other exclusions are explicit group decisions, never automatic guesses about business identities. Counts may overlap; exclusion previews show an upper bound because usable existing destination parents can keep children eligible. New scans can discover further dependent records.

Group corrections and exclusion decisions are stored outside the databases and match complete original source fingerprints. Exclusions are propagated through parent relationships, while existing valid destination parents remain usable. Saved exclusions can be undone for the next scan. Changed source rows require fresh decisions. No group action truncates, overwrites or imports destination records.

For empty destination line tables, the audit can also repair individual invalid or conflicting internal IDs when those particular IDs have no known incoming references. It preserves valid unique IDs and referenced IDs; known foreign keys, selected source references, lookup mappings and application-managed links are checked first. Assigned IDs exceed all observed source IDs and known reference values, and the corrected rows pass normal mapping, uniqueness, type and relationship checks. Unsupported references and retries disable this repair. An invalid empty-text mapping default for a nullable numeric column is normalized to NULL; populated values and explicit numeric defaults are preserved.

Refreshing the page or returning to Step 3 reconnects automatically to the selected tenant's active preview scan, including its current table, original elapsed time and Stop Scan control. It does not restart the scan or change its saved table selection. A simultaneous start from another browser tab also reconnects to the existing scan. Restarting the server still interrupts running scans.

Use **Stop Scan** during a Step 3 preview to cancel it. The panel shows **Stopping…** while the current database operation finishes and connections are released, then **Scan stopped**. Partial results are not a completed audit and cannot be imported; starting again runs a new scan from the beginning. Closing the page alone does not cancel the server scan. Audits started by a migration use that migration's existing Stop control.

While scanning, Step 3 shows one active table, its position in the selection (for example, table 3 of 21), the current operation, and a record progress bar where counts are known. The panel replaces the previous table when work moves on. Preparation, row checks, relationship checks and report saving are separate stages; completing a table's row scan does not yet confirm it is safe to import. The final report replaces the progress panel.

The wizard shows per-table counts, rule counts and sample findings. Download the JSON audit report and the newline-delimited JSON quarantine/review records from Step 3. The same downloads are available in migration results/history for runs that have an audit.

Reports and snapshots live under `data/quality-audits/<target-scope>/<audit-uuid>/`, which is ignored by Git. The scope includes target host, port and schema, so reports are not shared across tenants. Reports contain no connection credentials. Quarantine records include the full source row, mapped values, source table, row ordinal, action and reasons. Dates and binary values are preserved in the internal import snapshot. Keep these files with the tenant's migration records; they contain business data. Old audit directories can be removed after their evidence is no longer needed and no run is using them.

Correct flagged records in a working copy of the legacy database, repair the mapping or target conflict as appropriate, then run a fresh audit. The original source and quarantine evidence remain recoverable. This feature does not start a migration, alter a tenant's connections, or clean a live tenant merely by opening the wizard.

## Implementation and validation

The scanner reads Firebird within one read-only, repeatable-read transaction, orders rows by `RDB$DB_KEY`, checks the complete row count, and materializes BLOBs before closing the transaction. Complete rows are staged on disk; key indexes and findings are retained in memory. Accepted rows are written to separate snapshots after relationship checks converge. Preview scans run asynchronously with progress polling. Abort/read/persistence failures fail closed. Retry lookups can use a prior run's saved ID mappings only when their target records still exist.

Tests cover full scans beyond the first batch, arbitrary selected tables, selection scoping, missing identities, meaningful stock and financial values, open jobs, source/target duplicates, cascading parent rejection, unselected target dependencies, date/link scope, conversion errors, snapshot types, tenant isolation, source transaction lifecycle, runner gating and wizard rendering. Live database integration should be verified against a disposable copy of each new tenant before its production migration.
